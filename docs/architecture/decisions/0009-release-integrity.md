# ADR-0009: Release integrity

- **Status:** Accepted
- **Date:** 2026-10-02

## Context

People boot Sanctum on machines that may hold sensitive data, sometimes
during a security incident. They need to know the ISO they downloaded is the
one the project built, from the source it claims, and the project must meet
the source obligations of the GPL packages it redistributes.

Constraints from earlier decisions:

- The ISO is hosted on SourceForge or the project site, not on GitHub
  (ADR-0005). The maintainer uploads it by hand.
- No long-lived secrets in CI (the project brief).

## Decision

### What a release is

A release starts from a tag `vX.Y.Z` on a commit that is already on `main`.
`.github/workflows/release.yml`:

1. **Verify:** `scripts/release/check-release.sh` checks that the tag
   matches `VERSION`, `Cargo.toml` and `Cargo.lock`, that `CHANGELOG.md` has
   a dated section for the version, and that the tagged commit is on `main`.
2. **Build:** the same workflow as every pull request (`build-iso.yml`),
   from the tag, with both boot tests. Release builds use **no caches**, so
   nothing restored from an earlier run can reach a release. The package
   cache would be fairly safe, because pacman checks package signatures, but
   the Rust toolchain cache is not verified when it is reused.
3. **Publish:** only this job has write permissions (`contents: write`,
   `id-token: write`, `attestations: write`), and it runs in the `release`
   environment, which can require a reviewer's approval. It:
   - creates a **build provenance attestation** for the ISO, the source
     manifest and the package manifest,
   - drafts a GitHub release with the checksum, both manifests and release
     notes from the changelog.
4. **The maintainer**:
   - downloads the ISO from the run's artifacts (kept 30 days),
   - verifies it (`sha256sum -c`, `gh attestation verify`),
   - uploads it and the sources to the download host,
   - adds the download link to the draft and publishes it.

Tags are created by the maintainer and signed (`git tag -s`). A repository
ruleset should restrict who can create `v*` tags.

### Integrity

| Check | Protects against | How users run it |
| --- | --- | --- |
| SHA-256 file on the GitHub release | Corrupted or swapped downloads on the download host, because the checksum and the ISO come from different hosts | `sha256sum -c` |
| Build provenance attestation (Sigstore, through GitHub's OIDC token) | An ISO not built by this repository's release workflow from this tag | `gh attestation verify ISO --repo AbyssalOath/abyssal-sanctum` |

The attestation needs no stored signing key. GitHub stores it against the
file's SHA-256, so it works wherever the ISO was downloaded from.

**Not yet:** a minisign signature from an offline project key, which would
also protect against a compromised GitHub account or workflow. It needs key
custody, so it moves to Phase 8 and will reuse Abyssal Warden's key process.

### Source obligations (GPL)

The ISO redistributes Arch Linux binaries, many under the GPL. Each release
publishes `abyssal-sanctum-vX.Y.Z-x86_64.sources.txt`, generated by the
build. It lists every package base and version, with its Arch source tarball
and its packaging repository at that version.

Links alone are not enough. Arch's source server
(`sources.archlinux.org`) had only 56 of the 571 package bases in v0.1.0's
snapshot. The maintainer therefore **publishes the source tarballs next to
the ISO** on the download host for every release.
`scripts/release/fetch-sources.sh` collects them in the pinned builder
container: Arch's tarball where it exists, otherwise the package's Arch
packaging repository at the version tag, built with `makepkg --allsource`
(the PKGBUILD plus every upstream source, checked against the PKGBUILD's
checksums). Sanctum's own source is the tagged commit on GitHub.

## Consequences

- Attestations need a public repository (GitHub creates them for private
  repositories only on Enterprise Cloud). The v0.1.0 attest step failed
  while the repository was private, and passed once it was public.

- Releasing needs a few manual steps (upload, mirror sources, publish).
  `docs/operations/releasing.md` lists them in order.
- A release build downloads every package and the Rust toolchain again. It
  takes longer and uses the archive's bandwidth. Releases are rare enough
  for that.
- The download host must hold the ISO and the source mirror (several GB per
  release).
